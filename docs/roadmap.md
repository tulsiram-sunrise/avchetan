**Current phase: [Phase 8 — Finding and using data (v0.4.0)](#phase-8--finding-and-using-data-v040)**, planned 2026-11-10, then [v0.5.0 tasks, routines and reminders](#v050--tasks-routines-and-reminders) and [v0.6.0 security](#v060--security). v0.3.0 (Phases 6 and 7, the [app lock](#app-lock) and the [pre-release fixes](#pre-release-fixes)) was released 2026-11-09 ([v0.3.0](https://github.com/tulsiram-sunrise/avchetan/releases/tag/v0.3.0), PR #45). Each phase lists scope, deliverables and **done when** criteria (testable). Phases are sequential; a coding agent should finish a phase's criteria before starting the next. Advanced capabilities are specified in [product/advancements.md](product/advancements.md).

**Applies to every phase:** a phase that adds or changes user-visible behavior is done only when the matching [user-guide](user-guide/README.md) pages are updated ([onboarding & user docs conventions](conventions/onboarding-and-user-docs.md)).

**Order:** 1 → 2 → 3 → 4 → 5 → **5b (built-in Home Hub, directly after 5)** → *Public release milestone (when shipping to others)* → **v0.2.0 (Days view, more AI providers)** → 6 → 7 → **8 (v0.4.0)** → v0.5.0 → v0.6.0.

## Phase 5 — Server, sync, fallback, semantic search, deployment modes ✅

**Progress:** started 2026-11-02. `apps/server` has health, device registration, push and pull, token auth, the rate limit and body limit, on PGlite and starts as a hub. `@avchetan/sync` has the protocol schemas and the client engine. Tests cover two clients and a PGlite server through the engine. Both apps run the engine, with a Sync screen for addresses and the token. On 2026-11-02 a physical Android 14 phone and the desktop app synced through a hub on the PC: existing entries, new entries and an edit all crossed over, in 30–180 seconds, too slow for the 60-second target below. The hub's request log showed why: pushes arrived within 1.5 s of a capture, and the desktop polled every 59–61 s even with the dock hidden for 10 minutes, but Android pauses the app's timers while it is off screen. A change waiting out the 2 s push delay stayed on the phone until the app was opened again, and polls stopped too. The phone now pushes when it leaves the screen and when a change lands while it is off screen, and both apps poll every 30 s. Re-tested the same day on a release APK: an entry captured on the phone just before pressing Home, and one captured on the desktop, each appeared on the other device in about 30 seconds. `/v1/status` reports the server, its devices and the entries waiting or failed. The server has a Dockerfile (a bundled `server.mjs` plus PGlite, 91 MB compressed), a Postgres compose file for development and a Home Hub compose file, all tried on Docker here. CI runs the server tests on Postgres 18 as well as PGlite. Steps 1 and 2 are done. Step 3 has started: the server organizes entries other devices left waiting as one more device ([ADR-0021](decisions/0021-server-organizes-as-a-device.md)), using the apps' own extraction code, with the model from env; tested with the mock model on PGlite and Postgres, and started in Docker. The phone has a **Who organizes your entries?** choice (This phone or My hub, the `extraction.mode` setting); switching registers the phone again, and its waiting entries are taken at once. Tried on 2026-11-02 with the real phone (release APK, **My hub**) and the hub on the PC running Ollama `granite4.2:3b` on the processor: an entry captured on the phone came back organized in about 25–35 seconds, 32 s of it the model. Step 3 is done. Step 4: the hub keeps a vector for every entry (`log_embeddings` on pgvector, also on PGlite), `POST /v1/search` finds entries by meaning, and Ask on both apps has a `search_history` tool when a hub is set up; tested with a mock model on PGlite and Postgres, and in Docker against Ollama. Suggested model: Ollama `qwen3-embedding:0.6b` (1024 numbers per entry, about 0.2 s each on the processor). Tried on 2026-11-02 with the real phone and the hub on the PC: on its first start the hub embedded the 17 existing entries in one pass; an entry saying only "Left leg felt stiff climbing the stairs" was found by Ask for "when did my knee hurt?", with the hub answering the search in 79 ms. Step 4 is done. Step 5: `POST /v1/ask` answers on the server device's copy with the apps' own Ask and tools ([ADR-0022](decisions/0022-hub-answers-on-its-device.md)), streamed as server-sent events; the phone has **Who answers your questions?** (This phone or My hub). Tested with a mock model, including a tool call and a citation. Tried on 2026-11-03 with the real phone on **My hub** and the hub running Ollama `granite4.2:8b` on the processor: "when did my knee hurt?" came back with details and a citation in about 2 minutes (the model took 120 s). That is slow but works; a graphics card or a smaller model would cut it. Step 5 is done. Step 6: the desktop shows a pairing QR code (Settings → Sync → **Pair a phone**) built from `GET /v1/pairing` and its token, and can **Change token** (`POST /v1/token/rotate`); the phone scans it (`expo-camera`), keeps the addresses that reach the same server, and syncs; Today shows a setup card until the phone can organize entries. Several addresses per device and failover were already in place. Tested through the real server: a fresh phone paired from the desktop's code and synced, and a new token locked it out while the desktop kept syncing. Tested on the real phone (2026-11-03): it scanned the desktop's code and synced, and after **Change token** it scanned the new code and kept syncing. Step 7: **Your data** in desktop Settings and on the phone's More tab exports JSON plus a CSV per table, and each device keeps 7 daily SQLite copies. A PGlite hub writes a daily snapshot of its data folder (`hub-YYYY-MM-DD.tar.gz`, 7 kept), and `restore:hub` puts one back. Tested on the PC on 2026-11-03: the desktop made its first backup by itself (it passed `integrity_check`). The hub snapshot of the real data was 5.7 MB and took 11 s, and restoring it into a spare folder brought back all 25 entries, 3 devices and 22 search vectors. On the phone (2026-11-03): **Back up now** showed the latest backup, and **Export everything** wrote the JSON and CSV files into Downloads. Step 8: the cloud host is decided ([ADR-0023](decisions/0023-free-cloud-supabase-render.md): Supabase Free + Render Free), and [setup-cloud](user-guide/setup-cloud.md) walks through it with no terminal. Followed for real on 2026-11-04: a Render service built from the Dockerfile on Supabase Free, with the desktop switched to it, which uploaded its whole history (25 of 25 entries) and then a new entry within a minute. The real setup found four problems, now fixed in the guide and the server: Render builds `master` unless the branch is set; a password with `#` or `/` breaks `DATABASE_URL`; Supabase's Connect window shows the IPv6-only direct connection first; and Supabase publishes every table through its Data API around the sync token, so the guide turns that off and every server table has row level security on (checked: Supabase no longer marks the tables unrestricted). The [Home Hub guide](user-guide/setup-home-hub.md#run-the-hub-from-a-terminal-instead) now walks through running the hub today, from the source code with Ollama, with a firewall rule for the hub's port on private networks only, and the [Tailscale guide](user-guide/remote-access-tailscale.md) adds a rule for Tailscale addresses only; pairing already includes the PC's Tailscale address. Step 8 is done. **Done when:**

## Phase 5b — Built-in Home Hub (no Docker, no terminal) ✅

It starts in about 0.5 s, or 14 s the first time while it creates the database, and uses about 290 MB of memory. It stops cleanly within 0.1 s when its stdin closes, which is how the desktop app will stop it, and also when the app that started it is force-killed. Step 2: the desktop app runs the hub itself (`commands/hub.rs`): **Settings → Home Hub on this PC** turns it on with a model preset, it starts with the app and runs while the app is open (tray included), it restarts after a crash with growing waits and gives up after five quick crashes with a reason (`hub_port_in_use`, `hub_crashed`), and quitting stops it through its stdin. Its settings are in `hub/hub.json`, its data in `hub/pglite-data` under the app data folder, and its token in the keychain (`hub:server:token`), passed to it by Rust only. **Use data from a hub I ran before** copies an existing `pglite-data` folder in and keeps the token this PC syncs with. Tried on 2026-11-04 with the real data: the hub started by hand was stopped, its folder moved in, and the built-in hub answered with the same server ID; the phone kept syncing without pairing again, and an entry from it came back organized. **Change token** works for the built-in hub too: the hub takes its token at start, so the app saves a new one for both and restarts it (tried 2026-11-04: the phone was refused until it scanned the new code, then synced). Step 2 is done. Step 3: under **Home Hub on this PC** a checklist shows what the hub needs, each with its fix: Ollama running and the hub's models downloaded (**Download them**, with progress), the network Private (**Open network settings**), the firewall rules (**Allow phones to connect**, through Windows' own approval), Tailscale's address, and the phones the hub knows, with **Pair a phone** when there are none. A copy of the real snapshot restored in 13 s and came back with the same server ID and a new epoch. Then, from the app on 2026-11-04, the real hub was restored to its 16:28 snapshot: it came back with a new epoch, the data from before was kept beside it, and the PC noticed, sent everything again and pulled from the start (its cursor went from 421 to 481), ending synced. ## v0.5.0 — Tasks, routines and reminders

Agreed 2026-11-10 as the release after v0.4.0; to be planned in detail before it starts ([Q28](open-questions.md)). Reminders at a time and repeating tasks, on the phone first:
- Reminders are scheduled with Android's alarm system as local notifications (as the brief reminder is), so nothing runs in the background to wait for them.
- Tasks get a reminder time and a repeat rule (daily, weekly on chosen days, monthly): a schema change in both dialects and sync. Finishing a repeating task makes the next one with a derived ID, so two devices make it once. The repeat rule is the one routines use (below), so there is one repeat system.
- "Remind me at 4 pm to call the dentist" is read by extraction (a new prompt version with fixtures); a reminder can also be set by hand.
- Also from the audit: `/done` and `/undo` on the phone, reusing the fuzzy command matching.

Added 2026-11-11 (the user's points, decided one at a time):
- **Done with a note.** Finishing a task takes an optional note on how it went; **Partly done** records a percentage and keeps the task open. Ahead or behind is computed from `completed_at` against `due_date` ("2 days late"). Tasks get `completion_note` and `progress_pct`.
- **Routines: a regular schedule and daily chores.** One new synced `routines` table with the repeat rule and an optional time window, in two kinds: *assumed* (sleep, work hours: counted as happening unless an entry says otherwise) and *confirm* (chores such as a walk or watering plants: ticked off). Each day of a routine is one row with a derived ID from the routine and the date. On first use the app offers a starter list of chores to pick from (derived IDs from the starter key, so two devices don't make them twice); the user adds, edits and deletes freely. Confirmation is one checklist card on the day plus one evening notification, never one per chore; a logged activity that matches a chore ticks it. Repeating tasks share the repeat rule. An ADR decides the table shape and how occurrences are made.
- **The brief marks what was missed.** The daily brief gets a *Missed or behind* part: tasks due and not done, tasks only partly done, chores not confirmed, assumed routines an entry contradicts. Computed in code like the brief's other facts; the AI only phrases them. No schema change.
- **Day coverage** (a setting, off by default). Hours accounted for out of 24: logged `duration_min` plus assumed routines (sleep, work), with 15% of the day allowed for small things nobody logs. The rest is shown as *unaccounted*, not *wasted*, because an unlogged hour may have been rest. It relies on routines and on durations being right (Phase 8's metric editing), so it comes last.

Added later on 2026-11-11 (second round):
- **Finishing a task** grows from *done with a note*: done (with a note), partly done, **move** (Tomorrow · Next week · Pick a date…, on every task row on both apps) and **cancel** (`cancelled_at`: shown struck through, never counted as missed; **Delete** stays for "this wasn't a task"). Deletes in the main window show an undo message instead of asking *Are you sure?*; on the phone, swiping a task row right finishes it and left moves it to tomorrow.
- **The brief's first two lines:** *Moved forward* and *Friction* become one line each, **✓ Went well** and **! Needs attention**, at the top, with a mark and a colour; *Missed or behind* (above) becomes part of **Needs attention**.
- **Share to Avchetan:** Android's share sheet sends text or a link from any app into a capture.
- **Accessibility pass:** text size follows the system, visible keyboard focus, screen-reader labels, on both apps.

Planned days, at the same evenness as Phase 8 (to be confirmed when v0.5.0 is planned in detail): 1 task fields (done note, partly done, cancelled; schema and sync) · 2 task actions on both apps (move, cancel, swipe, undo message) · 3 routines engine and ADR · 4 the routines page and starter chores · 5 the chore checklist card and evening notification · 6 repeating tasks through routines · 7 reminders on the phone · 8 "remind me at 4" read by extraction · 9 the brief's Went well / Needs attention · 10 day coverage · 11 Share to Avchetan · 12 accessibility pass · 13 `/done` and `/undo` on the phone · 14 test build and release.

## v0.6.0 — Security

Agreed 2026-11-10 as the release after v0.5.0; to be planned in detail before it starts ([Q29](open-questions.md), [Q6](open-questions.md)):
- **Encrypted hub traffic on home Wi-Fi**, where today plain HTTP is allowed after the *trust this home network* warning. Standard, audited cryptography only (no home-made protocol). Leaning: request bodies encrypted with a key exchanged through the pairing QR (XChaCha20-Poly1305, `@noble/ciphers`), signed requests so the token never travels; a new protocol version and re-pairing. Alternative: HTTPS on the LAN with the hub's certificate pinned through the QR. An ADR decides.
- **Encrypted backups and exports** first, then the **PC's database** with SQLCipher (rusqlite's SQLCipher build, key in the Windows Credential Manager, a one-time conversion). The phone's storage is already encrypted by Android; the hub's PGlite can't be, so the guide keeps recommending BitLocker there.
